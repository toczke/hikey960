# AGENTS.md

Instructions for any AI agent (or human) working on this repository. Read this before touching device tree, kernel config, or anything under `drivers-import/`. These rules exist because every one of them was violated at least once already in this repo's history — see §6 for the incident log.

## 1. What this repo is

A port of a modern Linux/Armbian environment to the HiKey960 (Kirin 960 / hi3660) board, currently on branch `feature/kirin960-vpu-1080p`. Scope: bootloader, GPU (Mali-G71/Panfrost), HDMI output, and hardware video codec (`hi_vcodec` — VDEC decoder, VENC encoder). Goal for the current phase: hardware H.265/H.264 encode up to 3840×2400@30fps and 4×1080p30fps concurrent, on top of the already-substantially-working decoder.

## 2. The one rule everything else follows from

**A capability is only "done" if there is a file in this repo that proves it, and every doc claim links to that file.** Not a paragraph describing a test that was run — the actual `dmesg` log, the actual output bitstream, the actual `ffprobe`/SSIM result. If you can't point to the file, the correct status is `[BUILDS ONLY, UNTESTED]` or `[NOT YET IMPLEMENTED]`, never a percentage and never "verified."

Use exactly these three tags in every doc/README status table entry, nothing else:
- `[VERIFIED ON HARDWARE — <path to evidence>]`
- `[BUILDS ONLY, UNTESTED]`
- `[NOT YET IMPLEMENTED]`

## 3. Evidence directory — do not gitignore this, ever

`tests/results/<test_name>/` holds the proof for every hardware claim:
- `dmesg.log` — captured *during* the run, not after (start the capture before launching the test).
- `run.log` — exact command, exit code, timing.
- For decode: sample output frames (`sample_frames/*.png`) and, wherever feasible, an SSIM/structural comparison against a CPU-decoded reference — not just "non-zero bytes," which noise and garbage also satisfy.
- For encode: the actual output bitstream, plus `ffprobe` output run on your host confirming it's a valid, correctly-sized stream — an ioctl returning 0 proves nothing by itself.

`tests/vpu_hardware_results.json` (generated by `tests/run_vpu_benchmark.py`) aggregates these. If either doesn't exist yet, write it — don't publish a status table with numbers that aren't backed by this file.

If repo size from this directory becomes a real problem, solve it narrowly (e.g. gitignore only large raw `.yuv` output, keep logs/JSON/PNGs/bitstreams tracked). **Never `.gitignore tests/` wholesale** — that has already happened once (commit `b4b7f62`), deleted the entire evidence trail backing a status report, and left every evidence link in `README.md`/`docs/07-MULTIMEDIA_AND_GPU.md` pointing at nothing. It was recovered from git history (`git show 1d0c6d7:tests/...`) — the fact that it *could* be recovered doesn't make it OK to have happened; the recovered state must stay tracked going forward.

## 4. Ground truth hierarchy — when docs disagree, this is the order that wins

1. `configs/hikey960-defconfig` (what actually gets built) and the patch files under `patches/` (what actually gets applied) — these are ground truth over any prose.
2. A register dump or `dmesg` log you just captured — over any existing doc claim about register values or hardware state.
3. `docs/*.md` — only trust these once cross-checked against 1 and 2. This repo has had multiple docs directly contradict each other and contradict the actual defconfig (Panfrost on/off, ADV7533 register `0x1c` value, chip identity ADV7533 vs ADV7535) — assume any specific register value, flag, or config claim in prose could be stale until you've verified it against the current defconfig/patches or a live read.

If you find a new contradiction like this, do not silently pick one side — resolve it by direct measurement (I2C/register dump, defconfig grep, actual boot test) and update both places to agree, noting in the commit message which one was wrong and why.

## 5. Source code risk map — know which files you can actually fix

| Location | Nature | What you can do |
|---|---|---|
| `drivers-import/vcodec/hi_vcodec/vdec/omxvdec/*.c` | Real, modern C (OMX wrapper, `dma_alloc_coherent`-based memory management) | Fully editable — fix bugs here normally. |
| `drivers-import/vcodec/hi_vcodec/venc/drv/venc/venc_platform.c`, `venc_memory.c`, `venc_regulator.c` | Real, modern C — added to replace `drv_venc_intf.S`/`hi_drv_mem.S` | Fully editable — this is the good pattern; extend it rather than adding more assembly-compat shims. |
| `drivers-import/vcodec/hi_vcodec/vdec/vfmw/vfmw_v4.0/firmware/driver/HiVDHV400R004/*.S` (per-codec HAL: `vdm_hal_h264.S`, `vdm_hal_hevc.S`, `vdm_hal_vc1.S`, `vdm_hal_vp6.S`, `vdm_hal_vp8.S`, `vdm_hal_mpeg2/4.S`, `smmu.S`, `scd_drv.S`, etc.) | **Not source.** Raw GCC-emitted assembly, compiled against a ~2017-era kernel ABI at Huawei's internal CI (visible in `.file`/`.loc` debug directives). No `.c` was ever shipped. | You can only fix *linkage* (missing symbols via a compat shim, see `ion_compat.c`) — never the actual decode logic. Struct-layout mismatches between the old and current kernel are a real silent-corruption risk here, not a hypothetical. |
| `drivers-import/vcodec/hi_vcodec/venc/drv/venc/drv_venc.S`, `hal_venc.S`, `drv_venc_efl.S`, `drv_venc_buf_mng.S`, `drv_venc_queue_mng.S`, `drv_omxvenc.S`, `drv_venc_proc.S` | Same situation as the vdec HAL — frozen assembly, the actual encode logic, still 100% present despite the platform/memory/regulator layer being modernized. | Same constraint: linkage-only fixes. This is the highest-remaining-risk part of the whole codebase for the current encoder goal. |
| `drivers-import/vcodec/ion_compat.c` | Real C, but a pure linkage shim — most of its functions (`ion_alloc`, `hisi_ion_client_create`, etc.) are no-ops returning `NULL`/stub values. | Fine as a last-resort symbol-satisfier. Never describe code that only calls through this file as "using modern DMA allocation" in docs — check whether the real `memory.c`/`venc_memory.c` path is actually what's taken at runtime before claiming that. |

Before loading any `.S`-only file's driver on real hardware for the first time, check `docs/10-VPU_SOURCE_AUDIT.md` for its per-file risk verdict (`LINKAGE-ONLY RISK` vs `STRUCT-LAYOUT RISK`). Files marked `STRUCT-LAYOUT RISK` need a named human sign-off before hardware testing, not just an agent's own judgment call.

## 6. Physical hardware safety protocol

This board has demonstrated real, not hypothetical, failure modes:
- **AXI bus lockup** requiring a full power cycle (not just reset) — first seen with DPE/SMMU misconfiguration, documented in `docs/07-MULTIMEDIA_AND_GPU.md` §1.
- **Kernel oops → board stops responding to ping, needs hard power cycle** — seen from a use-after-free in `processor_bpp.c`'s decoder teardown path.
- **Fragile EFI/UFS boot layout** — `docs/02-EDK2_AND_FLASHING.md` and `docs/03-POST_FLASH_STABILIZATION.md` document a bootloader that can leave the board needing serial/fastboot recovery on a bad flash.

Before any test session that loads new/modified kernel modules or touches DTB/bootloader:
1. Have a known-good fallback image on hand.
2. Prefer serial console over SSH-only for anything touching VDEC/VENC/DPE — if the AXI bus locks up, SSH just dies with no diagnostic; serial console is often the only way to see what actually happened.
3. Set up a hardware watchdog (or confirm one is active) before starting encoder bring-up specifically — the encoder touches the highest-risk frozen-assembly surface in the repo (§5) and concurrent multi-stream testing is the most likely place for a struct-layout bug to actually manifest.
4. Run anything you expect to pass at least 5–10 times in a loop before calling it stable — several bugs in this repo's history were intermittent (frame-count-dependent EOS timing, state that only broke in batch runs but not isolated runs) and a single clean pass does not rule them out.

## 7. Commit hygiene

- Atomic commits, one fix per commit, message states what was *tested*, not just what changed. (Compare the useful `a5a4d08`/`e2ce3aa`-style messages — specific bug, specific root cause, specific fix — against the original single 76MB `733b422` squash commit that made this whole repo impossible to audit for months.)
- A commit that updates a hardware-status claim in `docs/07-MULTIMEDIA_AND_GPU.md` or `README.md` may **never** also delete or gitignore the evidence files that claim links to (see §3 and §6 of the incident log below).
- If you retract a previous claim, say so explicitly in the doc and commit message ("previously reported as X, retracted because..."), don't just quietly change the number.

## 8. Incident log (why these rules exist — don't relitigate these)

1. **Single squashed commit.** The entire initial port (~76MB across GPU/HDMI/VPU) landed in one commit (`733b422`), making it impossible to tell which claim came from which experiment. Fixed going forward by atomic commits (§7).
2. **Contradictory docs, never cross-checked.** `docs/01` said to disable `CONFIG_DRM_PANFROST`; the actual defconfig had it enabled; `docs/07` claimed it was fully working. Three ADV7533/ADV7535 lane-count register values were claimed across three files (`0x1c=0xc0`, `0x1c=0x40`, `0x16=0x18`), none reconciled. Fixed going forward by the ground-truth hierarchy (§4).
3. **Unverifiable "92% complete" report.** A status report claimed 9/10 streams "verified on silicon" with precise frame counts and byte-validation percentages, while the same report listed the benchmark script that would generate those numbers as not-yet-run. No result JSON or test vectors existed in the repo to check the claim against. Fixed going forward by the evidence-first rule (§2, §3) — and this rule *did* subsequently produce real evidence (`tests/vpu_hardware_results.json` in commit `1d0c6d7`, with real SSIM numbers and honest partial/fail results for several streams).
4. **Evidence deleted right after being created.** Commit `b4b7f62`, in the same breath as writing an honest, evidence-backed status update, gitignored `tests/` and deleted every file the update relied on. Recovered from git history; must not recur (§3).

Do not "clean up" `tests/results/` to make the repo look tidier. The mess of logs and PNGs in there is the entire point — it's what separates this repo's claims from the ones in incident #3.
